# Contributing

Found a **security flaw**? Don't open an issue: read [`SECURITY.md`](SECURITY.md) — the channel is
private by construction.

## Running it

```bash
bun install                                   # at the root: it's the bun workspace
cd packages/storymap-ui
bun run build && bun run start                # comes up at http://127.0.0.1:3008
```

Point it elsewhere with `STORYMAP_TARGET=/path/to/repo` if you don't want it operating on this same
repository. To iterate, `bun run dev` — which is **not** `next dev`: it's the app's own entrypoint
(`bun run build:server` + `node dist/ah-server.mjs`) with `AGILEHARNESS_DEV=1`.

**Don't bring up `next dev` on the side.** This isn't a style preference; they are two measured
defects:

1. **The app owns the `upgrade` event, and Next doesn't.** The entrypoint is `src/server/main.ts`
   bundled into `dist/ah-server.mjs` precisely because `next start` doesn't handle `upgrade` — and
   that's where the terminal's WebSocket is authenticated by the SAME session as the panel, with an
   `Origin` check. Under `next dev` that listener goes back to Next (HMR needs it) and the check stops
   covering everything. That's why `AGILEHARNESS_DEV=1` never goes to production — absent = production,
   which is the safe side.
2. **A server action called from the client doesn't resolve** (measured on 2026-07-13): the POST goes
   out, the server answers 200 in ~150ms, and the promise on the client neither resolves nor rejects.
   Counters and popovers freeze in their initial state and you spend the afternoon fixing code that
   was already correct. The SAME code, in the SAME checkout, works with a production build.

In other words: any screen check that depends on a server action is valid **only** on a production
build.

## The suite

```bash
cd packages/storymap-ui
bunx tsc --noEmit          # typecheck
bunx vitest run            # the whole suite
bun run lint
```

The subject of the suite is the two demo boards (`storymap/boards/demo`, `demo-legado`) — synthetic
data, which is why they travel with the repository.

## What CI will demand of your PR

It runs on every PR, with no access to secrets (it's `pull_request`, never `pull_request_target`):

- **licenses** — a new strong-copyleft dependency in the runtime closure fails, and so does a package
  with no declared license (absent ≠ permissive);
- **containment prerequisite** — the runner installs `bubblewrap` and `socat` and then **proves**
  bwrap comes up, because a suite running in the downgraded posture would go green having checked a
  different product;
- **lint of the workflows themselves** — no interpolating PR text into `run:`, no `uses:` without a
  40-hex SHA, minimum `permissions:` declared;
- **typecheck** — twice, and the second pass is not redundant: page prop contracts live only in
  `.next/types/**`, generated by the build, so a first pass on a clean clone cannot see them;
- **lint**, **build** and the **suite**;
- **secret gate** over the published tree;
- **SBOM + OSV + VEX** (`security.yml`, which also runs weekly — a new advisory shows up without
  anyone touching the code).

Two things review demands that CI has no way to measure: **an assertion is never weakened to make it
pass** — the fix goes in the target, never in the ruler; and **a new protection ships with the test
that fails without it**. A declared capability that no test produces is the #1 defect shape in this
codebase.

## There is no CLA

No CLA, no DCO bot, no extra signature. §5 of Apache-2.0, which already licenses this repository,
states that any contribution submitted for inclusion is licensed **under the terms of that same
license**, with no additional terms — *inbound = outbound*. Asking for a signature on top of that
would be ceremony with no new legal effect, and one more step between you and your first patch.
