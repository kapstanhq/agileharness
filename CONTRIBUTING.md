# Contributing

Found a **security flaw**? Don't open an issue: read [`SECURITY.md`](SECURITY.md) — the channel is
private by construction.

## Running it

```bash
bun install                                   # at the root: it's the bun workspace
cd packages/storymap-ui
bun run build && bun run start                # comes up at http://127.0.0.1:3008
```

Point it elsewhere with `AGILEHARNESS_TARGET=/path/to/repo` if you don't want it operating on this same
repository. To iterate, `bun run dev` — which is **not** `next dev`: it's the app's own entrypoint
(`bun run build:server` + `node dist/ah-server.mjs`) with `AGILEHARNESS_DEV=1`.

**Don't bring up `next dev` on the side.** This isn't a style preference; they are two measured
defects:

1. **The app owns the `upgrade` event, and Next doesn't.** The entrypoint is `src/server/main.ts`
   bundled into `dist/ah-server.mjs` precisely because `next start` doesn't handle `upgrade` — and
   that's where the terminal's WebSocket is authenticated by the SAME session as the panel, with an
   `Origin` check. Under `next dev` that listener goes back to Next (HMR needs it) and the check stops
   covering everything. That's why `AGILEHARNESS_DEV=1` never goes to production — absent = production,
   which is the safe side.
2. **A server action called from the client doesn't resolve** (measured on 2026-07-13): the POST goes
   out, the server answers 200 in ~150ms, and the promise on the client neither resolves nor rejects.
   Counters and popovers freeze in their initial state and you spend the afternoon fixing code that
   was already correct. The SAME code, in the SAME checkout, works with a production build.

In other words: any screen check that depends on a server action is valid **only** on a production
build.

## The suite

```bash
cd packages/storymap-ui
bunx tsc --noEmit          # typecheck
bunx vitest run            # the whole suite
bun run lint
```

The subject of the suite is the two demo boards (`storymap/boards/demo`, `demo-legado`) — synthetic
data, which is why they travel with the repository.

## What CI will demand of your PR

It runs on every PR, with no access to secrets (it's `pull_request`, never `pull_request_target`):

- **licenses** — a new strong-copyleft dependency in the runtime closure fails, and so does a package
  with no declared license (absent ≠ permissive);
- **containment prerequisite** — the runner installs `bubblewrap` and `socat` and then **proves**
  bwrap comes up, because a suite running in the downgraded posture would go green having checked a
  different product;
- **lint of the workflows themselves** — no interpolating PR text into `run:`, no `uses:` without a
  40-hex SHA, minimum `permissions:` declared;
- **typecheck** — twice, and the second pass is not redundant: page prop contracts live only in
  `.next/types/**`, generated by the build, so a first pass on a clean clone cannot see them;
- **lint**, **build** and the **suite**;
- **secret gate** over the published tree;
- **SBOM + OSV + VEX** (`security.yml`, which also runs weekly — a new advisory shows up without
  anyone touching the code).

Two things review demands that CI has no way to measure: **an assertion is never weakened to make it
pass** — the fix goes in the target, never in the ruler; and **a new protection ships with the test
that fails without it**. A declared capability that no test produces is the #1 defect shape in this
codebase.

## Publishing a release (maintainers)

AgileHarness is generic software, but it is developed against real, private boards. Anything that
names that private context — a real card id, a product or person name, an e-mail, a machine — must
never reach this repository. Three scripts keep that true:

```bash
node scripts/oss/publication-gate.mjs --base origin/main --tree --require-terms   # what would leak?
contrib/ah-verify                                                                  # gate + typecheck + whole suite, bound to the tree
contrib/ah-publish                                                                 # dry-run; add --yes to push
```

- **The gate** measures two things. The *ratchet* reads the lines a change **adds** and applies every
  rule, including the shape heuristics (something that looks like a card id, a path under a user's
  home directory). `--tree` reads **every line** of `HEAD` and applies the exact rules: the
  maintainer's private terms, e-mails and machine hosts — nothing published, new or old, may carry
  them. Generic rules ship in the repo. The maintainer's own list of private names (products,
  people, services, real card ids) lives **outside** the repository, one term per line, in
  `$AH_OSS_PRIVATE_TERMS` or `~/.config/agileharness/oss-private-terms`: if the list lived here, the
  list would be the leak. With `--require-terms` a missing list fails the run. A line that genuinely
  needs a term carries `oss-allow: <reason>` on it or on the line above.
- **Example ids.** When a test or a comment needs a card id, use the reserved namespace
  `<type>-ex0000` (four digits, e.g. `story-ex0042`): it has the shape of a real id and the gate
  accepts it. For hosts use loopback, private ranges or the documentation ranges (RFC 5737); for
  e-mail, `example.*` / `*.test`.
- **Examples are invented, never derived.** A term list only finds what someone listed. Text
  *copied* from the private boards — a persona, a canvas, a card question used as a test fixture —
  carries no listed term and still describes a real product. `node scripts/oss/derivation-check.mjs
  --names` cross-checks every tracked file against the maintainer's private sources (declared, one
  directory per line, in `~/.config/agileharness/oss-private-sources`): a six-word run shared with
  a private card or document, found in a test, fixture, skill or doc and absent from the runtime
  source, is a copy. So is a persona or system name declared in a private `board.yaml`. Rewrite
  those from scratch in the demo vocabulary — swapping the nouns of a real sentence is not
  inventing, and the check cannot see it. Lines the tool itself composes at runtime (and a private
  card merely stored) are recorded as accepted, also outside the repo.
- **`ah-verify`** writes a receipt keyed by the *tree hash* of `HEAD` — any edit invalidates it.
- **`ah-publish`** does not push the private history: a clean net diff can sit on top of commits
  whose messages and intermediate states are not clean. It builds ONE commit holding `HEAD`'s exact
  tree (parent: what is already public, message: the summary, also run through the gate), pushes
  that commit as a fast-forward — never forced — and the version tag. It refuses a dirty tree, a
  public branch the local one does not contain, a tag that already exists, a gate failure and a
  missing `ah-verify` receipt. The public commit is signed by `$AH_PUBLISH_AUTHOR_NAME` /
  `$AH_PUBLISH_AUTHOR_EMAIL` when set (a project identity), otherwise by the local git identity;
  the dry-run prints which one.
- **`ah-publish --new-history`** is for the case where what is *already* public carries private
  context: cleaning the tree does not clean old commits. It publishes `HEAD`'s tree as a parentless
  commit and removes the old remote tags. On an empty repository that is a plain push. On a
  repository that already has the branch it is a forced replacement (`--force-with-lease`, pinned
  to the public commit it checked) and only a person may do it: the script asks for the repository
  name on a terminal and refuses without one. It cannot reach what the hosting service keeps on its
  own — old commits reachable by hash, pull-request refs, forks.

## There is no CLA

No CLA, no DCO bot, no extra signature. §5 of Apache-2.0, which already licenses this repository,
states that any contribution submitted for inclusion is licensed **under the terms of that same
license**, with no additional terms — *inbound = outbound*. Asking for a signature on top of that
would be ceremony with no new legal effect, and one more step between you and your first patch.
